# 朗读进程（运行时）清单

**完整的参考实现**是 `references/desktop-companion/tts_worker.py`。它摘自作者的开源桌宠 [Desktop Companion](https://github.com/Bf190t/mac-desktop-companion)，MIT 许可，已经过真机验收：
- 0.6B Base，只学音色，流式；
- 第一声约 0.12 秒，比实时快 3 倍左右；
- 内存约 3.3 GB。

它要依赖原项目的其他文件，只用来读和照抄，不能直接运行。

作者自用的**读书 app** 原来的朗读进程和它不一样：
- 用的是 CustomVoice，不流式，整段生成完才播；
- 没有取消，也没有独占协议输出的处理；
- 有自己的保护：token 上限校验、失败的段拆小重试。

下面每一条都对应一个实际踩过的坑。

## 声音固定

- **参考录音只加载一次**：`mlx_audio.utils.load_audio(path, sample_rate=model.sample_rate)` 得到 `mx.array`，之后每段都传同一个对象。
  - 有多个声音时，存成 `{声音 id: mx.array}`。
  - 不要每段换参考，也不要拿上一段的输出当下一段的参考，否则会一路越漂越远。
- **每段生成前都重设同一个种子**：`mx.random.seed(SEED)`。种子不能保证不漂，因为文字不同，采样的路线就不同；但它能保证同一句话每次念出来一样，方便复现和缓存。
- **语言固定**：Base 用 `lang_code="chinese"`，CustomVoice 用 `language="Chinese"`。不要用 `auto`，中英混排时会换口音。
- **不要在运行时用 VoiceDesign**：它每次调用都会按描述重新"造"一个人。它只用来做候选，用完可以删掉（1.7B 约 4 GB）。
- **不要靠降 temperature、加提示词去压漂移**：
  - 读书 app 用了温度 0.6 加"同一位讲书人、保持音高"的提示，偏的段反而更多；
  - 更早的实验里，温度再降就会念不停。
- 0.6B CustomVoice 不认 `instruct`；Dylan、Eric 两个内置声音会自动转成方言口音。
- **换参考录音时**：把参考录音的 sha256 加进朗读缓存的键和进程指纹里。否则会混着播旧声音，进程也不会重启。

## 文字

- **新 app**：直接用 `scripts/tts_text.py`，可以复制进项目。
- **已有 app**：保留它自己的分段，只借文字清理那几条。已保存的朗读进度、缓存键都依赖原来的段号。
- 文字清理：
  - 去掉引号和书名号。单独的「”」「……」会被念成 1–6 秒的杂音；
  - 省略号、破折号改成逗号；
  - 中文里的钟点改成口语（8:30 → 8点半，7:05 → 7点零5分），不改会漏读或读错；
  - 只有标点的段不念，粘到前一段；
  - 拉丁字母拼接时保留空格（不要变成「Really?Yes!」）。
- 新 app 的分段：在句末切，每段最多 80 字。段越长，一次生成里的变数越多。
- 时长上限 `max(4, 字数×0.45+4)` 秒，`max_tokens = ceil(上限×12.5)`。
  - 判断念跑了，看 token 数是否到了 `max_tokens`：mlx-audio 的 `token_count` 不含结束符，到顶就说明模型没自己停下来。
  - 正常语速是每字 0.20–0.25 秒。

## 内存和速度

- 只设 `mx.set_cache_limit(256 * 1024 * 1024)` 不够：整段一次生成时，0.6B 的峰值仍约 6.7 GB（读书 app 测）。
- 要配合流式生成（`stream=True, streaming_interval=0.32`，每块约 0.32 秒音频）一起用，峰值才能降到约 3.3 GB（桌宠测）。
- 每段念完调一次 `mx.clear_cache()`。
- mlx-audio 0.6.4 和 0.6.5 在裁尾部静音上有差别：0.6.4 可能多裁一点。测试要在 app 自己的环境里跑。

## 进程和播放（要做"边生成边播"时）

- 协议用 JSON 行，一行一个对象：`speak` / `cancel` / `quit`。新的 speak 自动取消正在念的那一条，最新的优先。
- 协议输出要独占一个文件描述符：`out = os.fdopen(os.dup(1), "w")`，然后 `os.dup2(2, 1)`。这样库打印的东西不会混进 JSON。
- 父进程看门狗：每 2 秒 `os.kill(parent_pid, 0)` 一次，父进程不在了就退出。
- 退出用 `os._exit(code)`：读 stdin 的守护线程还卡在 read 里时，正常退出会报 exit 134，macOS 会当成崩溃。
- 预热：加载完先念一个「嗯。」，第一句真话就和后面一样快。
- App 端（Swift）的做法：
  - AVAudioEngine 加 AVAudioPlayerNode，每条一个 player，完成回调用 `.dataPlayedBack`；
  - 8 秒收不到新音频就判定卡住，重启朗读进程；
  - 加载失败后先退避一段时间再试，不要反复拉起。

## 可选：偏了就重念（守门）

**首选声纹守门（读书 app 实测）**：0.6B Base 只学音色时，偶尔有一段整段像换了个人，音高却只差 1–2 个半音，音高守门抓不住。做法：每段念完，用同一个 Base 模型的 `extract_speaker_embedding` 算声纹，减去 `assets/speaker_background.json` 的平均后和参考的声纹求余弦；低于 0.7 就换种子（原种子 +7919）重念一次，留更像的那版。读书 app 两章 66 段：正常段对参考 0.83–0.95，跑偏的一段 0.31，重念后 0.84；正常段从不触发，所以几乎不增加耗时。现成的实现是 `scripts/voice_guard.py` 的 `VoiceGuard`，可以整段复制进 app。

下面是较早的音高守门，只在没有 Base 编码器时当后备：

每段生成后算音高中位数（`voice_audio.f0_median`）。偏离参考超过约 4 个半音时，换个种子重念一次，只重试一次。

门槛不要设低：正常朗读每段本来就会偏离参考 ±3 个半音左右，设低了会白白重念。

读书 app 早先 14 段的实验结果：
- 重念对其中 6 段有效；
- 另外 8 段只从偏 52 Hz 降到偏 41 Hz；
- 总耗时多了约 75%。

所以它只能当补丁用，不能代替"先把参考声音定下来"。

## 安装

- 模型按 revision 固定版本，逐个文件校验 sha256。参考：
- `references/desktop-companion/install.py`：固定版本，逐个文件核对大小和 sha256；装完先念一遍，确认能出声才算装好；
- `scripts/get_base_model.py`：同样的下载和核对，单独可用；
- `assets/base_model_manifest.json`：0.6B Base 8bit 的文件清单。
- Python 依赖用带哈希的锁文件。
- `engine.json` 记录这些：模型路径、revision、每个声音的参考录音路径和 sha256、包版本、安装自检结果。
- 安装完先试念一句，没有声音就判定安装失败。
- 参考录音和它的说明 JSON 跟 app 一起打包：用的模型、描述或说话人、种子、原句、谁在哪天选的。
